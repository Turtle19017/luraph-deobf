# 019 — VM68 mode-215 opcode semantics

## Scope

Block #1 deserializes an object whose late metadata identifies:

```text
dispatch_id = 68
vm_mode     = 215
entry_pc    = 4453
stack_size  = 130
slot_count  = 4474
```

The outer J9 handoff calls the method selected by `q[q[1]]`, so block #1
dispatches to `B[68]`.

`B[68]` resolves eight parallel per-slot arrays from the object and returns a
closure. In the `mode == 215` branch, one array is read directly as:

```lua
opcode = s[pc]
```

where `s = q[q[10]]`. This is the third serialized count-sized table.

The source-derived lane binding is:

```text
opcode  = q[q[10]]   serialized table3
S       = q[q[12]]   serialized table1
w       = q[q[13]]   serialized table2
H       = q[q[8]]    serialized table4

aux_v   = q[q[15]]
aux_I   = q[q[11]]
aux_V   = q[q[16]]
aux_K   = q[q[14]]
```

## Trust boundary: serialized vs finalized lanes

The serializer allocates the four auxiliary arrays with no dense prefix. An
initial post-B:A snapshot attempt observed:

```text
B[3] = nil
#aux_v = #aux_I = #aux_V = #aux_K = 0
```

at the outer handoff. The zero sequence lengths do **not** prove the auxiliary
tables are empty because they may be sparsely populated.

The same capture proves the outer block1 path did not execute the source branch
`state35 -> B[3]`; B:A returned successfully while B[3] was nil. The outer
post-fill path must therefore use the state451 closure-reuse/build side.

The first probe attempted ordinary table indexing plus `tostring` on arbitrary
auxiliary values and triggered protected code through probe-side metamethod
evaluation before the entry marker completed. It did not establish finalized
lane contents.

The corrected probe uses `rawget` for every lane lookup and only renders
scalar values directly, preventing both `__index` and `__tostring` side
effects. That snapshot remains the trust boundary for promoting serialized
tuples into actual runtime tuples.

## Mode-215 instruction groups

The complete source mapping is machine-readable in:

```text
receipts/luraph_VM68_mode215_semantics.json
```

The useful semantic families are:

```text
control flow
  1, 15, 20, 27, 48

return
  19, 59

self-rewrite/decode
  23, 38, 47, 49, >=62 except 63

calls / nested dispatch
  6, 10, 26, 30, 34, 36, 44, 57, 60

object/runtime access
  2, 3, 7, 14, 25, 28, 35, 46, 50, 51

vararg / pack
  13, 22, 52, 54

bulk moves
  8, 11, 24, 39
```

Arithmetic/comparison operations make up most of the remaining opcodes.

## Notable opcodes

### Opcode 52 — vararg load/pack

```text
N = w[pc]
p = S[pc]

copy first N-1 varargs into R[p ...]
R[p + N - 1] = table.pack(select(N, ...))
```

This corrects an earlier interpretation that opcode 52 loaded the current
object.

### Opcode 39 — four-slot register move

```text
R[w[pc+0]] = R[S[pc+0]]
R[w[pc+1]] = R[S[pc+1]]
R[w[pc+2]] = R[S[pc+2]]
R[w[pc+3]] = R[S[pc+3]]
pc += 3
```

The common loop increment then advances to the slot after the four-slot group.

### Opcode 15 — direct encoded jump base

```text
pc = w[pc]
```

The common loop increment occurs after the handler.

### Opcode 23 — in-place self rewrite

Opcode 23 transforms the current `S/w/H/opcode` tuple through build-specific
32-bit arithmetic, decrements the program counter, and causes the rewritten
slot to be executed again on the next iteration.

This is a major reason raw serialized lane values cannot be interpreted as a
static bytecode stream without modeling rewrite instructions.

### Opcode 48 — mode switch

```text
mode = w[pc]
pc   = S[pc] + 1
break to the outer B[68] mode dispatcher
```

So a single object can transition between interpreter submodes.

### Opcode 30 — nested object dispatch

Opcode 30 resolves a nested object from an auxiliary lane, assembles capture
descriptors, recursively dispatches it with:

```text
B[obj[obj[1]]](B, nil, captures, obj)
```

and stores the resulting callable/object into a register.

This is the runtime counterpart of the nested serialized-object structure seen
during B:A parsing.

## Current block-1 serialized entry

Offline serialized lanes give the candidate bootstrap beginning at pc 4453.
Those tuples remain explicitly marked **serialized** until the finalized-lane
snapshot is observed.

The project should prefer reachable-path lifting after that snapshot rather than
attempting to symbolically execute all possible mode-215 opcodes.
